Problem

Reliable answers start with knowing which source applies.

A current catalog, an expired quotation and an unapproved update can give different values for the same product. Finding a matching sentence alone does not tell an employee which value to use.

The prototype separates approved facts, historical terms and pending changes, and leaves unsupported fields unverified.

System

How the system works

01

Find the product and its sources

Search product identifiers and documents for relevant evidence.

02

Show what supports the answer

Answers link to source excerpts. Old terms remain dated and missing information stays unverified.

03

Review proposed changes

A reviewer compares the current and proposed values, then approves or rejects the update.

04

Refresh answers after approval

Approved changes retain history. An admin refreshes the search index before the demonstrated answer and its evidence reflect the new value.

Why this matters to a business

The workflow is designed to reduce information mix-ups. Its controls are demonstrated in a local synthetic prototype; fewer errors or faster work have not been measured in a company.

Use the right version

Employees can inspect a source and distinguish current product facts from old quotation terms.

Review before changing policy

Product-data owners should confirm the product, effective date and source before a reviewer approves an update; admins then control the index refresh.

Make mistakes inspectable

Keep the old value and decision history. If an answer is unsupported or answers the wrong question, investigate its source and scope.

Knowledge governance

New information is a proposal. Not yet a fact.

In the recorded synthetic workflow, a proposed MOQ changes from 144 to 180 units. The Reviewer compares both values and their source versions, then records a decision. Pending or rejected proposals cannot overwrite current authority; approved replacements preserve the prior value and audit history.

Pending → Approved / Rejected; approved facts may later be Superseded.

Separate responsibilities, explicit permissions.

Employee

Ask questions and inspect evidence and Product Master.

Reviewer

Review proposed facts, record decisions and inspect audit history.

Admin

Stage validated sources and control ingestion and reindex jobs.

Explore the technology and its limits

Exact SKU/product ID lookup, dense retrieval and BM25 are combined with RRF and authority-aware heuristics. SQLite stores approved facts; Qdrant stores the rebuildable search index. Answers are composed from evidence fields.

The public answerer is local and extractive; no answer-generating LLM is enabled. Multilingual MiniLM via FastEmbed / ONNX is optional. The reproducible demo and reported benchmark use the non-neural deterministic hash fallback.

Evaluation

Technical evaluation: retrieval is not answer accuracy

The internal frozen holdback used 20 developer-agent-authored synthetic questions. Average relevant-source coverage in the top 5 results was 92.5%; a separate automated answer check passed 17 of 20 (85%).

Scope & limitations

This small internal benchmark uses deterministic hash fallback + BM25/RRF and automated source/substring checks. All human-review fields are unreviewed. It is not independent human validation, neural embedding evaluation, enterprise answer accuracy or measured ROI. The separately named held-out split reports different results.

A known failure in the separately named held-out split (PH-006) answers a request for archived terms with a current minimum order and omits the old price. A cited value can still answer the wrong question. Other failures include partial identifiers and incidental wording.

Evidence & outcomes

An end-to-end workflow, made reproducible.

The synthetic recording verifies an approved change from 144 to 180, retained history, and a cited 180 answer after controlled reindexing. The public v1.0.0 release contains documentation, frozen evaluations, Docker configuration and CI checks; this does not establish enterprise deployment.

Public data. Explicit boundaries.

All business records are synthetic: no proprietary company, customer or private quotation data. Uploads are bounded, validated, sensitivity-scanned and quarantined; browser tokens stay in memory, not localStorage. Private runtime data is excluded from Git. These are demo controls, not an independent security audit or a deployed enterprise service.
